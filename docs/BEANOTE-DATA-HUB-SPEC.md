# Beanote 데이터 허브 화면 명세

- 문서 ID: `beanote-data-hub`
- 상태: 구현 전 초안
- MVP: Phase 1 T1 Export
- 대상 화면: 데스크톱 관리자 콘솔, 반응형 읽기 지원

## 1. 화면의 단일 목적

운영자가 **어떤 데이터를 어떤 근거와 권한으로 누구에게 반출했는지** 생성부터
만료까지 추적할 수 있어야 합니다.

기존 **유저 데이터** 화면은 한 건의 스캔을 보고 OCR 결과를 검수하는 화면입니다.
데이터 허브는 여러 건을 데이터셋 단위로 반출하고 API 접근을 통제하는 화면입니다.
두 화면에서 같은 기능을 중복 제공하지 않습니다.

## 2. 정보 구조

```text
운영 현황
유저 데이터
데이터 허브
├─ 수집 현황
├─ 내보내기
├─ API 접근       # Phase 2, MVP에서는 안내·비활성 상태
└─ 승인·감사
```

기본 진입점은 **수집 현황**입니다. 마지막으로 사용한 하위 탭을 계정별로
기억할 수 있지만 URL은 각 영역에 고유해야 합니다.

권장 경로:

```text
/admin/data-hub/overview
/admin/data-hub/exports
/admin/data-hub/api-clients
/admin/data-hub/audit
```

실제 Beanote 콘솔의 라우팅 관례가 다르면 경로명은 바꿀 수 있습니다. 하위 영역의
책임은 유지합니다.

## 3. 공통 화면 요소

### 3.1 헤더

- 제목: `데이터 허브`
- 설명: `수집 데이터의 반출, 외부 API 권한, 승인 및 감사 기록을 관리합니다.`
- 환경 배지: `운영` 또는 `스테이징`
- 정책 상태:
  - `정책 승인됨`
  - `정책 검토 중 — 실제 사용자 데이터 반출 불가`
- 주 작업 버튼:
  - MVP: `내보내기 생성`
  - 정책 미승인 시 disabled, 이유를 버튼 가까이 표시

### 3.2 권한

| 역할 | 수집 현황 | Export 생성 | T2/T3 승인 | API Client 관리 | 감사 조회 |
| --- | --- | --- | --- | --- | --- |
| 소유자 | 조회 | T1 | 가능 | 가능 | 전체 |
| 데이터 관리자 | 조회 | 정책으로 허용된 tier | 불가 | 조회 | 허용 범위 |
| 검수 운영자 | 요약 조회 | 불가 | 불가 | 불가 | 본인 작업 |
| 읽기 전용 감사자 | 조회 | 불가 | 불가 | 메타만 | 전체 |

MVP에서는 `소유자`만 Export를 생성할 수 있습니다. 기존 관리자 권한을 소유자
권한으로 자동 승격하지 않습니다.

### 3.3 공통 상태 언어

상태는 색만으로 구분하지 않고 텍스트와 아이콘 또는 모양을 함께 사용합니다.

| 상태 | 의미 | 허용 작업 |
| --- | --- | --- |
| `queued` | 작업 대기 | 취소 |
| `running` | 파일 생성 중 | 상세 보기 |
| `ready` | 다운로드 가능 | 다운로드, 폐기 |
| `failed` | 생성 실패 | 오류 보기, 재생성 |
| `expired` | 만료되어 다운로드 불가 | 동일 조건으로 새로 생성 |
| `revoked` | 소유자가 조기 폐기 | 감사 보기 |

## 4. 수집 현황

### 4.1 독자 질문

“지금 어떤 데이터가 얼마나 쌓여 있고, 외부로 제공해도 되는가?”

### 4.2 상단 요약

- 전체 데이터셋 수
- T1 제공 가능 데이터셋 수
- 마지막 수집 시각
- 정책 또는 동의 blocker 수
- 최근 24시간 Export 수

수치는 전체 DB가 아니라 현재 선택한 환경을 기준으로 합니다. 마지막 갱신 시각을
표시하고 수동 새로고침을 제공합니다.

### 4.3 데이터셋 표

| 열 | 의미 | 표시 규칙 |
| --- | --- | --- |
| 데이터셋 | 영문 ID + 한국어 설명 | 예: `scan_fields` · OCR 필드 |
| privacy tier | 최소 필요 등급 | T0~T3 |
| 행 수 | 현재 활성 행 | 천 단위 구분 |
| 최신 데이터 | 가장 최근 `updated_at` | 사용자 시간대로 표시 |
| 결측률 | 핵심 필드 기준 | 분모와 계산 시점 tooltip |
| 보존기간 | 현재 정책 | 무기한 대신 실제 규칙 |
| 동의·처리 근거 | 정책 문서/버전 | 링크 또는 blocker |
| 외부 제공 | 가능/검토 중/불가 | 이유를 함께 표시 |

데이터셋 행을 열면 다음 상세를 보여줍니다.

- 필드명, 타입, nullable
- 품질 상태별 건수
- 출처 테이블 또는 파이프라인
- 대표 예시는 합성 데이터만 표시
- T2/T3 필드는 기본 접힘
- 실제 OCR 원문·이미지·자유 메모 미리보기 금지

### 4.4 현재 수집 범위 카드

첨부된 “현재 실제 수집 범위” 표를 데이터 허브 안에 유지한다면 정적 설명이
아니라 데이터 카탈로그에서 파생해야 합니다. 수동 문구와 실제 DB가 어긋나지
않도록 다음 필드를 카탈로그로 관리합니다.

```text
field_id
display_name
dataset_id
collection_state
privacy_tier
retention_policy
consent_basis
external_sharing_state
recommended_action
```

`사진`의 권장 처리는 `단말 원본과 분석용 이미지를 구분`이 아니라 더 정확히
다음처럼 표시합니다.

- 정제된 소스 이미지: EXIF/GPS 제거 및 재인코딩된 입력 이미지
- 분석용 이미지: OCR 또는 후속 파이프라인을 위해 변환된 이미지

## 5. 내보내기

### 5.1 독자 질문

“승인된 범위의 재현 가능한 데이터 묶음을 만들고 안전하게 받을 수 있는가?”

### 5.2 목록

| 열 | 의미 |
| --- | --- |
| Export ID | 복사 가능한 안정 ID |
| 생성 시각 | 요청을 접수한 시각 |
| 요청자 | 운영 계정 표시명 |
| 목적 | 필수 입력한 이용 목적의 짧은 요약 |
| 데이터셋 | 선택한 데이터셋 수와 목록 |
| tier | T1~T3 |
| 기간 | 데이터 시간 범위 |
| 포맷 | JSONL 또는 CSV |
| 상태 | queued~revoked |
| 만료 | 다운로드 만료 시각 |
| 건수/용량 | ready 이후 표시 |

기본 정렬은 최신 생성순입니다. 상태, 요청자, tier, 데이터셋, 생성일로
필터링합니다.

### 5.3 생성 흐름

`내보내기 생성`은 한 화면 또는 짧은 단계형 form으로 구성합니다.

#### 1단계 — 목적과 수령 대상

- 목적: 필수, 20~500자
- 수령 조직 또는 시스템: 필수
- 재제공 여부: 기본 `금지`
- 요청 티켓/승인 문서: 선택 링크

#### 2단계 — 데이터 범위

- 데이터 기간: 필수
- 데이터셋:
  - 기본 선택: `brew_logs`, `scans`, `scan_fields`
  - 선택: `candidates`, `corrections`, `assets` 메타데이터
- privacy tier:
  - MVP: T1 고정
  - T2/T3: disabled와 사유 표시
- 철회·삭제:
  - `revocations.jsonl 포함` 고정, 해제 불가

#### 3단계 — 포맷과 만료

- 포맷:
  - `JSONL — 기계 분석 권장`
  - `CSV — Excel·BI`
- 파일 묶음: ZIP
- 다운로드 유효시간: 기본 24시간, 최대 72시간
- 사진 포함: MVP disabled
- OCR Raw 포함: MVP disabled
- 자유 메모 포함: MVP disabled

#### 4단계 — 최종 확인

최종 확인에는 “무엇이 포함된다”보다 다음을 먼저 보여줍니다.

- 제외되는 민감 항목
- 데이터셋·기간·예상 행 수
- privacy tier와 승인자
- 링크 만료와 재다운로드 방법
- 감사 로그에 기록되는 내용

확인 문구:

```text
이 Export가 승인된 목적과 수령 대상에만 사용되며 재제공되지 않음을 확인합니다.
```

### 5.4 생성 결과

생성 요청 성공 시 즉시 파일을 반환하지 않고 Export 상세로 이동합니다.

- `queued/running`: 진행 상태, 시작·최근 갱신 시각
- `ready`: 파일명, 용량, 데이터셋별 행 수, checksum 검증 안내, 만료
- `failed`: 사용자에게 안전한 오류 요약과 내부 `request_id`
- `expired/revoked`: 다운로드 버튼 제거

다운로드 URL은 짧게 만료되고 한 Export에 종속되어야 합니다. URL 자체를 감사
로그나 일반 애플리케이션 로그에 남기지 않습니다.

### 5.5 Export 상세 감사 타임라인

```text
요청 → 승인 → 생성 시작 → 생성 완료 → 다운로드 → 만료/폐기
```

각 이벤트에 시각, actor, 동작, IP 또는 세션 메타데이터의 정책상 허용 범위,
결과, `request_id`를 기록합니다.

## 6. API 접근

### 6.1 MVP 상태

Phase 1에서는 읽기 전용 안내 화면을 제공합니다.

- 상태: `Phase 2 준비 중`
- API를 직접 활성화할 수 없음
- Data API v1 계약 문서 링크
- 현재 생성된 Client가 있다면 메타데이터만 표시

### 6.2 Phase 2 목록

| 열 | 의미 |
| --- | --- |
| Client | 이름과 client ID prefix |
| 수령 조직 | 계약된 외부 주체 |
| scopes | 허용 resource와 tier |
| 상태 | active, suspended, revoked |
| 생성·만료 | credential 수명 |
| 최근 사용 | 마지막 성공 호출 |
| 호출량 | 선택 기간 요청 수 |

### 6.3 Client 생성

- Client 이름
- 수령 조직
- 이용 목적
- 허용 scopes
- 최대 privacy tier
- 데이터셋/필드 제한
- 만료일
- IP allowlist 선택
- rate limit
- 승인 문서

secret은 생성 직후 한 번만 표시합니다. 이후에는 prefix, 마지막 네 글자 또는
credential ID만 표시하고 원문 복구 기능은 제공하지 않습니다.

### 6.4 키 회전·폐기

- 회전은 짧은 overlap 기간을 지원
- 폐기는 즉시 적용
- `suspend`와 `revoke`를 구분
- 모든 작업은 재인증과 감사 이벤트 필요
- 실제 사용 중인 키는 최근 사용·호출량을 보여준 뒤 확인

## 7. 승인·감사

### 7.1 독자 질문

“누가 무엇을 왜 보고 내보냈고, 철회가 실제로 반영됐는가?”

### 7.2 승인함

MVP T1 소유자 Export는 self-approval 정책을 명시적으로 기록할 수 있습니다.
T2/T3는 최소 다음을 요구합니다.

- 요청자와 승인자 분리
- 목적, 수령자, 데이터셋, 기간
- 필드·asset 단위 접근 범위
- 승인 만료
- 재인증
- 승인/거절 사유

### 7.3 감사 이벤트

| 이벤트 | 반드시 기록할 내용 |
| --- | --- |
| Export 생성 | 요청자, 목적, 필터, tier, dataset, 예상 건수 |
| Export 승인/거절 | 승인자, 결과, 사유, 정책 버전 |
| 생성 완료/실패 | 실제 건수, 용량, checksum, 오류 코드 |
| 다운로드 | Export ID, actor, 시각, 결과 |
| 만료/폐기 | 자동/수동 구분, actor |
| API Client 생성 | 조직, scope, tier, 만료 |
| 키 회전/폐기 | 대상 credential, overlap, actor |
| API 호출 | client, endpoint, status, 건수, request ID |
| 철회 반영 | revocation ID, 영향 resource 수, 완료 시각 |

감사 검색은 기간, actor, 조직, Export/API Client, action, status로 필터링합니다.
감사 로그에는 secret, OCR 원문, 이미지 URL, 자유 메모를 넣지 않습니다.

## 8. 오류와 빈 상태

| 상황 | 화면 동작 |
| --- | --- |
| 정책 미승인 | Export 버튼 비활성 + 승인 필요 항목 링크 |
| 데이터 없음 | 빈 표 대신 수집 범위와 필터 해제 안내 |
| 집계 지연 | 마지막 계산 시각 표시, 재계산 작업 중복 금지 |
| Export 실패 | 안전한 오류 요약 + request ID + 재시도 |
| 링크 만료 | 새 Export 생성 안내, URL 재활성화 금지 |
| 권한 부족 | 존재 여부를 과도하게 노출하지 않는 403 화면 |
| API 장애 | 기존 ready 파일 접근과 감사 조회는 가능한 한 유지 |

## 9. 접근성과 반응형 기준

- 탭은 키보드로 이동 가능하고 현재 탭을 텍스트로 식별
- 모든 표 헤더와 행 이름을 시맨틱하게 연결
- 상태를 색으로만 표현하지 않음
- 긴 ID는 중간 생략하되 전체 복사 가능
- 좁은 화면에서는 표 전체를 카드로 바꾸기보다 핵심 열을 먼저 표시하고 상세로 이동
- 생성 form 오류는 필드 근처와 요약 영역에 함께 표시
- 진행 상태는 자동 갱신하되 스크린 리더에 과도하게 반복 공지하지 않음
- 시각은 사용자 시간대로 표시하고 원 UTC 값도 상세에서 확인 가능

## 10. MVP 인수 조건

| 시나리오 | 통과 조건 |
| --- | --- |
| 일반 관리자 접근 | Export 생성 불가 |
| 소유자 T1 Export | 허용된 dataset·기간으로 queued 생성 |
| 정책 미승인 | 실제 사용자 데이터 Export 생성 차단 |
| T2/T3 선택 | 비활성 또는 승인 흐름 없이는 제출 불가 |
| 사진·자유 메모 | MVP bundle에 없음 |
| ready 다운로드 | 만료 URL과 checksum 제공 |
| 만료 후 접근 | 파일 다운로드 불가 |
| 조기 폐기 | 즉시 revoked, URL 무효 |
| 모든 상태 전이 | 감사 타임라인에서 확인 가능 |
| 철회 발생 | `revocations.jsonl` 포함 및 영향 건수 기록 |
| 실패 | 사용자 오류와 내부 request ID 분리 |

## 11. 구현 전 확인

- 실제 콘솔의 역할 모델에서 `owner`를 어떻게 판별하는가?
